# Fitness

Offline-first Expo / TypeScript app for iOS and Android. Product scope: [MVP](docs/MVP.md),
visual system: [Design](docs/DESIGN.md), progress: [Plan](docs/PLAN.md).

## Local development

Node 22.13+; Xcode and an iOS simulator; Android SDK + Java 17 and an emulator.

```sh
npm ci
npm run ios
npm run android
# Once native builds are installed:
npm start
npm run typecheck
npm test
```

Development builds are used, not Expo Go. For a physical iPhone, build with Xcode signing
(team `2UNNRK9L5Q`) and start Metro on the LAN (`npx expo start --dev-client --lan`); the phone
and Mac must share a network. Native folders are generated by Expo
prebuild and ignored. `eas.json` includes dev, preview and production profiles; no
EAS project, account, hosting, ad service or purchase service has been created.

## Approved offline content

The current published release from `fitness-automation/releases` is bundled (v0.3.0: 30
exercises, male and female, white-background H.264 loops and posters, body views, heroes and
equipment icons). Screens use the typed repository interface in `src/content/types.ts`. Do not
edit the generated `bundled.json`, `bundled-assets.ts` or `hit-regions.json`.

To re-import after a new release (requires Python 3):

```sh
npm run content:import -- /Users/oktayshakirov/Coding/fitness-automation/releases
```

The importer follows `current.json`, checks the `content.json` digest and every media file's
size and sha256, and converts the hit-test SVGs to polygons for body taps. Full media
attribution is bundled and visible in Profile. Never edit the rendering repo from this app
workspace.

## Remote content (M6)

With `EXPO_PUBLIC_CONTENT_URL` set to a directory holding `current.json` (the layout
`fitness-automation/releases` already has), the app checks it on launch and on foreground
(every time in development, at most every 6 hours in release builds). A newer release is
downloaded, checked against `current.json` and every file's size and sha256, and staged.
It takes effect at the next app start, never mid-session; Profile offers a restart. Files the
bundle or an earlier download already has (same sha256) are not fetched again. Startup uses
the active release, then the previous one, then the bundle; a host that points back at the
bundled version returns the app to its bundle. Unset URL = bundled content only. Logic and
tests: `src/content/remote.ts`, `tests/remote.test.ts`; device IO: `src/content/device.ts`.

Local end-to-end check (no hosting):

```sh
python3 scripts/make_test_release.py   # v0.3.1 = v0.3.0 + a mirrored push-up, in work/remote-fixture
python3 -m http.server 8790 --bind 127.0.0.1 -d work/remote-fixture
EXPO_PUBLIC_CONTENT_URL=http://127.0.0.1:8790/ npx expo start --dev-client --localhost --clear
```

On Android also run `adb reverse tcp:8790 tcp:8790`. Open the app once (Metro logs
`[content] {"status":"staged",...}`), restart it, then run `.maestro/remote-content.yaml`.

## Native checks without rebuilding

Reuse the installed development builds unless native dependencies or configuration
changed. On this host, start Metro with IPv4 resolution:

```sh
NODE_OPTIONS=--dns-result-order=ipv4first npm start -- --localhost
```

With the development app connected, run Maestro against an explicit device:

```sh
MAESTRO_CLI_NO_ANALYTICS=1 maestro --device DEVICE_ID test .maestro/library.yaml --test-output-dir work/qa
MAESTRO_CLI_NO_ANALYTICS=1 maestro --device DEVICE_ID test .maestro/navigation.yaml --test-output-dir work/qa
MAESTRO_CLI_NO_ANALYTICS=1 maestro --device DEVICE_ID test .maestro/tracking.yaml --test-output-dir work/qa
```

Run one Maestro process per device and wait for it to exit before starting another.
Keep source code fixed during each flow: live reload can invalidate navigation and
local form state. After a timed-out XCTest run, stop its remaining runner before
retrying. Development-client restart checks wait for the JavaScript app to load
before opening a route. Tracking tests create and remove their own new entry;
failed runs may leave sample entries in the test device.

The tests exercise functional behavior. They do not establish packaged offline
startup, physical-device playback/lifecycle behavior or 60 fps performance.

`.maestro/log-day.yaml` logs one exercise for yesterday and undoes it (Log sheet day stepper).

For iOS tracking, use `.maestro/tracking-ios.yaml`: it verifies reps/weight via
steppers plus typed notes, persistence and Undo. Direct numeric typing on iOS is
still an open verification item after XCTest stalled while changing numeric fields.
Android's tracking flow covers typed reps and weight. The optional Body flow is
`.maestro/body.yaml`; its current acceptance covers the recovery list, not unapproved
body images or hit regions.

Restart the development app after source changes before native acceptance runs;
iOS may retain an older bundle when Fast Refresh is unavailable.

### Profile and backup checks (M5)

Run `.maestro/settings.yaml` for first-run choice, preferences and Privacy. Restart
that device's app process, reconnect the development URL if needed, then run
`.maestro/settings-persistence.yaml`. Expected saved choices: female, lb, slow.
The approved bundle falls back to available male media until female assets ship.

For Android backup tests, push `.maestro/fixtures/backup.json` to
`/sdcard/Download/fitness-test-backup.json`, then run `.maestro/backup-android.yaml`.
It imports one synthetic log, repeats the import without duplication, and opens
native sharing. Dismiss sharing before running `.maestro/backup-units.yaml`, which
checks 40 kg → 88.18 lb → unchanged save → 40 kg. Tests leave synthetic local data.
On iOS, put the same fixture in simulator Files, choose it with Import data, and
check the confirmation/result; export should open the native JSON share sheet.
No account or cloud file provider is required. Native picker layouts vary by OS.
