# Wear OS companion: brief

Give Android users the same watch features the Apple Watch app has (read-only recovery glance, Pro only).
Target release: 1.2.0. Same scope as the Apple Watch version, nothing more: no logging from the watch,
no workout tracking, no standalone mode.

## What exists today (read these first)

- `targets/watch/index.swift`: the watchOS app. It shows a circular gauge with the recovered %, "recovered",
  a streak line when the streak is above 0, then either "All muscles ready. A good day to train." or a "Resting"
  section listing each muscle with its "ready in" text. It recomputes every 60 s. There are two empty states:
  no data yet ("Open Muscle Pal on your iPhone to see your recovery here.") and not Pro ("Muscle recovery on
  your watch is part of Muscle Pal Pro.").
- `targets/watch/Recovery.swift`: the payload type (`WidgetData`), the display rules (`Recovery`: drop
  muscles whose `readyAt` has passed, percent = (total - resting) / total, streak only if the last log was
  today or yesterday) and `readyIn` ("ready in ~5 h" / "ready in ~2 days"). The rules mirror `widgetView` in
  `src/widget/data.ts`, which has tests in `tests/widget.test.ts`.
- `targets/watch-complication/index.swift`: watch face complications (circular gauge, corner, inline
  "72% recovered", and rectangular "Muscle Pal / 72% recovered / Chest, Back"). They use a timeline with an
  entry at each `readyAt`, so they stay correct with no phone around.
- `modules/watch-connectivity`: the phone side, iOS only. `sendToWatch(json)` pushes the newest summary with
  `updateApplicationContext`, where the newest value wins and is delivered when the watch is reachable.
- `src/widget/sync.tsx`: builds the summary (`buildWidgetData`) on every log, settings or Pro change and when
  the app goes to the background. iOS sends it to the watch. Android currently only feeds the home screen
  widgets.
- Colours: lime `#C8FA3C` on black.

## What to build

### 1. Phone side: an Android implementation of `modules/watch-connectivity`

- Add an Android platform to the local Expo module (`expo-module.config.json`, Kotlin module named
  `MusclePalWatchLink`, the same `send(json: String)` function). Add
  `com.google.android.gms:play-services-wearable` to the module's Gradle file.
- `send` does a `Wearable.getDataClient(context).putDataItem` on path `/recovery`, with key `data` holding the
  JSON string, `setUrgent()`. A DataItem behaves like application context: the newest one wins, and it syncs
  when a watch connects or installs the app later.
- Fail silently when there is no Play Services or no watch (catch `ApiException`). The phone must never
  crash or wait on this.
- `modules/watch-connectivity/index.ts`: load the native module on Android too.
- `src/widget/sync.tsx`: in the Android branch, also call `sendToWatch(JSON.stringify(data))`.

### 2. The Wear OS app: `targets/wear/`, native Kotlin

The folder lives in the repo next to the iOS targets. `android/` is gitignored and regenerated by
`expo prebuild`, so nothing may live only in `android/`.

- A Gradle module with `applicationId com.shadev.musclepal`. It must match the phone exactly, or the Data
  Layer never connects. Set `minSdk 30` (Wear OS 3), and match `compileSdk`/`targetSdk` to the phone
  (`rootProject.ext`).
- Manifest: `<uses-feature android:name="android.hardware.type.watch" />` and
  `<meta-data android:name="com.google.android.wearable.standalone" android:value="false" />`, because it
  needs the phone for data.
- **Data:** a `WearableListenerService` filtered to path `/recovery`. It stores the raw JSON in DataStore
  (or SharedPreferences), then asks the Tile and the complications to refresh. On first launch, also read
  the current DataItem, in case the phone sent it before the watch app was installed.
- **Recovery rules:** port `Recovery.swift` (`Recovery`, `readyIn`) to Kotlin with the same wording. Add
  JVM unit tests for the same cases as `tests/widget.test.ts`.
- **App (Compose for Wear OS, Material 3):** a `ScalingLazyColumn` with the same content and empty states as
  `targets/watch/index.swift`. Change "iPhone" to "phone" in the copy. Recompute every minute while it is
  visible.
- **Tile:** a Tile is the Wear equivalent of the glance people use most. Use `TileService` + ProtoLayout:
  an arc progress showing the %, the % text, the streak and up to 3 resting muscles, with a tap that opens
  the app. Give the Tile a timeline with an entry at each future `readyAt` so it updates by itself. Show the
  Pro and no-data states as short text.
- **Complications:** use `SuspendingTimelineComplicationDataSourceService` and return a
  `ComplicationDataTimeline` with an entry at each future `readyAt`, which is the same idea as the iOS
  timeline. Support `RANGED_VALUE` (circular gauge), `SHORT_TEXT` ("72%") and `LONG_TEXT`
  ("72% · Chest, Back"). When not Pro, show a lock icon or "Pro". When there's no data, show "Open app".
- Icon: reuse `assets/brand` (round launcher icon). Name: "Muscle Pal".

### 3. Wiring it into the build: a config plugin

- Add `plugins/withWearApp.js` and register it in `app.json` `plugins`. On prebuild it must:
  - add `include ':wear'` and `project(':wear').projectDir = new File(rootDir, '../targets/wear')` to
    `android/settings.gradle`, so the sources are not copied and stay in `targets/wear`;
  - make sure the Compose compiler Gradle plugin version matches the Kotlin version the root project uses
    (`android.kotlinVersion` in `android/build.gradle`). A mismatch is the most likely build failure.
- The debug build of the Wear app must sign with the same `debug.keystore` as `android/app`, or the phone and
  watch debug builds won't pair over the Data Layer.
- Versions: `targets/wear/build.gradle` reads `app.json` (`expo.android.version` and `versionCode`), so there
  is one source of truth. Use `versionName` = phone version and `versionCode` = 1_000_000 + phone
  versionCode, because Play requires a unique versionCode for every bundle in the app. Document this in
  `docs/STORE.md`.
- Check that `npx expo prebuild --clean -p android` followed by `./gradlew :app:assembleDebug :wear:assembleDebug`
  works from a clean checkout.
- Release bundles: `./gradlew :wear:bundleRelease`. Store AABs must be signed with the same upload key as
  the phone app. Ask Oktay how phone AABs are produced today. If it's EAS, add an eas.json profile for the
  watch with `"android": { "gradleCommand": ":wear:bundleRelease" }`. Do not create a new keystore.

### 4. Version and docs

- Bump the phone to 1.2.0 and the next versionCode in `app.json`, and also in the locally generated
  `android/app/build.gradle` if it exists (see the 2026-11-16 PLAN entry).
- README: add a "Wear OS" part next to "iPad and Apple Watch" covering the module, the plugin, how to run it,
  and the version scheme.
- `docs/STORE.md`: add the Wear OS form factor, the Wear screenshot requirement and the versionCode scheme to
  the checklist.
- `docs/PLAN.md`: add a dated entry with what was built and verified, and what wasn't.
- Privacy: the in-app Privacy screen and `portfolio` `privacy-policy/muscle-pal.html` should mention that
  the recovery summary is sent to a paired watch, as it is for the Apple Watch (the portfolio page still
  lacks the Apple Watch line too). Play's Data safety answers stay "no data collected", because the data
  goes phone to watch only.

## Verification

Oktay has no physical Android phone or Wear watch, so this is emulator-only. Say so in the PLAN entry.

1. `npm run typecheck`, `npm test`, and the Kotlin unit tests.
2. Create a Wear OS emulator (Wear OS 5, large round) and pair it with the existing phone emulator through
   the Wear OS app on the phone emulator, or `adb` pairing (Android Studio > Device Manager > Pair Wearable).
   The Mac's disk runs near full: before creating the AVD, check free space on `/System/Volumes/Data` and
   reuse an existing phone AVD.
3. Install the debug builds of both. Log a workout on the phone and check that the watch app, the Tile and a
   complication on a watch face update. Check Pro and non-Pro (dev Pro toggle or RevenueCat sandbox) and the
   no-data state on a fresh install.
4. With the phone emulator stopped, advance time (or wait for a short recovery) and check that the Tile and
   complication count down by themselves.
5. Check text on a small round screen (Wear OS small round AVD). Clipped text is a common Wear review rejection.
6. Take Wear screenshots for the Play listing (`assets/screenshots/Android/Wear`).

## Out of scope

- Logging or editing workouts from the watch (it would need two-way sync; iOS doesn't do it either).
- Health Services, heart rate and workout sessions.
- Samsung-specific (Tizen) watches. Galaxy Watch 4 and later run Wear OS and are covered.
- Uploading to Play Console. Oktay does that: add the Wear OS form factor, a Wear OS release track, the
  screenshots, and submit.

## Done means

From a clean checkout, `expo prebuild` + Gradle builds both modules. On paired emulators the watch app, Tile and
complications show the same numbers as the phone's home screen widget, for both Pro and non-Pro. They count
down without the phone. Tests pass, the docs are updated, and the release AAB for `:wear` builds signed with
the upload key (or the step that remains is written down).
